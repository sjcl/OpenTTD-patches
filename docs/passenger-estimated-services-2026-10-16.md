## 接続と時刻の分離

確定時刻表の `Compile()` と Timed planner の条件を維持し、不成功時に
`CompileEstimated()` で別の duration-only pattern を作る。通常の旧方式を
選択している間は、この追加コンパイルを行わない。

`period > 0` は Certified、`period == 0 && estimated_period > 0` は Estimated、
両方0は Unsupported。この分類は時刻表の周期・所要時間に対するもので、実車の
位相の確定性は別の `phase_known` で扱う。完全な時刻表でも未知位相なら待ち時間を推定する。
推定の arrival/departure は累積所要時間であり、絶対時刻や
確定周期ではない。推定周期を NextDeparture、位相捕捉、departure index に渡さない。
既存の EstimatedServiceIntent/EstimatedBoundService を使い、公開サービスの
certainty と照会結果の `estimated_service` で確定ダイヤとの違いを保持する。

Order occurrence、乗降mask、強制降車、NoLoad/NoUnload、営業停車順序を保持する。
Waypoint と継続可能な Depot は時間の中に含め、停車駅にはしない。
条件分岐・ジャンプ・refit・停止/売却等の Depot を含む系統は Unsupported にする。
無条件ジャンプや停止Depotの後ろに書かれた区間は、境界を切るだけでは実在する
運行の証明にならないためである。グラフは区間境界を表現・検証できるが、OrderListの
部分区間抽出には制御フローと反復運行の証明が必要で、今回は実装していない。
施設を検証できない車両は、時刻が不明なだけの車両と区別して従来どおり除外する。

## 推定係数

計算はすべて整数で、サービス世代の構築時に行う。

| 項目 | 使用値と根拠 |
|---|---|
| 区間所要時間 | 宣言済み値、正の未確定記録値、距離推定の順。混在する既知区間を保持 |
| 距離推定 | Manhattan tile距離× train 4 / road 8 / ship 16 / aircraft 2 tick、加速等16 tick、航空機の空港余裕128 tickを加算 |
| 座標がない経由指令 | 距離8 tile相当。幾何学値は経路の存在判定には使わない |
| 未計測の停車待ち | 10 tick、航空機32 tick。宣言済み0は保持 |
| 所要時間の不確実性 | 未確定記録値は区間時間の1/8、距離推定は1/4を一般化コストに加算。乗車時間の診断値とは分離 |
| 未知位相の待ち | `ceil(3 * circuit / (4 * effective_fleet))`、`effective_fleet = min(8, floor(sqrt(N)))` |
| 位相不明車両数N | 実在する異なる車両だけ。既知の同時発車車両を未知位相の増便として数えない |
| 不確定dispatch | 少なくとも半周期を待つ。slot所有権や等間隔運転を仮定しない |
| 既知位相との混在 | 実際の既知発車streamによる半最大gapと、未知側の期待待ちの小さい方 |
| 容量リスク | gap / 最大単車定員（64席で打切り）の切上げ。未知情報には待ちの1/8、最大64 tickの追加余裕 |
| 乗換 | 既存設定を維持。接続の物理的な最短乗換時間と一般化ペナルティを分ける |

未知位相に対する車両数の効果は sqrt で抑え、団子運転の余地を残す。1台の
3/4周期は等間隔運転を仮定した1/2周期より保守的で、従来の全周期待ちより小さい。
これらは初期の工学的ヒューリスティックであり、実績による統計推定ではない。
全区間0のダイヤも、0 tickの高速接続にはせず距離推定へ戻す。

共通区間では物理的な停車prefixと乗降条件が同じ実在の全区間rideだけを束縛する。
推定系統同士でもprefixの先を別車両へ接ぎ木しない。既知の発車streamの集約を維持し、
未知側には最短単独周期と最長周期による抑制した車両数効果を比較して使う。

分散用の第二候補は、従来の一般化コスト+25%に加え、乗車時間の増加を
`max(32 tick, 最良候補の1/4)`、乗車回数の増加を1回までに制限した。
一般化コストで勝った経路自体はこの分散制限の対象外であり、合理的な高速遠回りを
直線距離だけで拒否しない。乗換後は、到着系統が新表にない場合も初乗車用の
ランダム分散を再適用しない。

## 実行、性能、保存

旅客ごとの全国探索や車両一覧走査は追加していない。停車構造・コスト・共通区間は
サービス捕捉と共有グラフの構築時に計算する。表照会、Journey/Legacy/Fallback索引、
Packetイベント、到着時の集団検証を引き続き使う。推定サービスの loading 観測では
OrderListの再走査をせず、保存されたサービス更新キューへ更新を任せる。

実乗車は既存の RebindPrecomputed / ValidatePassengerServiceRide を通し、実Order、
occurrence、施設、NoLoad/NoUnload、強制降車、refit、乗換時刻、容量・予約、
incarnation/generationを検査する。初回の推定だけで実車へ予約しない。

共通区間の先頭rideを実車へ束縛した際、その実車が目的地まで連続して運べるなら、
凍結された停車列の費用と、予定降車地点からの既存の後続費用を比較する。
乗り通しが高くならない場合だけ、実車の目的地Orderまで延長する。強制降車、
NoUnload、施設、世代をnative validatorで再検査し、直前系統の除外による帰り道を
避ける。検査結果は車両/cargo/Intent/目的地の乗車コンテキストで共有する。
コンパイル済みの1系統の局所走査で、旅客ごとのOrderList・車両一覧・全国探索ではない。
乗換が大幅に速い場合は延長しない。部分乗車で残ったPacketは元のIntentを保つ。
この延長は同一実車が最終目的地へ到達する場合を対象とする。複数の後続乗換地点を
比較して降車地点を再構成する一般化は未実装である。分散制限とこの修正を合わせても、
一般化費用の最適経路すべてについて再訪がないことを証明したものではない。

短時間の実輸送で、表の乗車系統とliveのincarnation/generationが一致していても、
無関係な町の道路工事やテンプレート交換処理が全系統をunsafeにしていることを確認した。
駅以外のBuildRoad/Terraform/LandscapeClearでは停車契約を無効にせず、Build/Sell/
Move/Autoreplace/TemplateReplaceは実際に変わる共有OrderListを通知する。
駅撤去等の保守的な無効化と実乗車検査は維持する。単にIntentの寿命を短くする変更はない。

停車順序・乗降maskが一致するサービスは、時刻表の確定状態が変わっても既存表の
費用を凍結したまま新しいgenerationへ更新できる。古いgenerationのrideは引き続き拒否する。
照会結果のestimatedフラグは更新後のサービスを示し、旧保存表の再生には旧条件を維持する。

JPSD blobはv9、拡張feature `passenger_periodic` はv11。CargoPacketのレイアウトと
RideKindは追加していない。推定周期、区間境界、品質、現行/保持グラフのアルゴリズム
flagを保存する。v1–v8は読み込み可能。古い表は元の費用・操作数で分割再生し、
未対応系統は通常の保存済み更新キューへ入れる。サーバー/クライアントでロード中に
異なるローカルcacheや壁時計から推定し直さない。

改善率やLegacy985.75との同等性を、この補助追跡だけから主張しない。

初期照会には直通525・一般化費用9,848・乗車300・期待待ち9,196tickがあり、
路線の欠落ではない。実際に照会された3393の候補261件はすべて補助分類`allowed`で、
131件の実乗車を記録した（完了130件と途中観測1件）。長待ちの標本64は
3,181,107,135に発生し、3,181,114,094に525へ乗り、485tick後に到着した。
照会時は524のIntent、実乗車記録はcurrent=1の525で、空席667を記録した。
この標本について乗車時点の条件拒否や容量不足は記録されていない。
ただし未照会の列車まで網羅した記録ではないため、待ちの全原因や全乗車機会の
取りこぼし不存在を証明したものではない。期待待ちの較正と、実運行間隔・乗車機会の
追加診断は残る。単なるIntent期限短縮は行っていない。

重点追跡の初期標本はPacket中点が通常抽出と異なる場合がある。上の単一初期旅客の
比較を置き換えず、対象OD内でも長い残り時間が残ることを示す補助結果として扱う。
生CSV、独立集計、再集計スクリプトは最終証跡の `focused-od-details.json` と
`checks/analyze-focused.py.gz` に保存した。

## 保存復元

長時間輸送終了セーブと性能終了セーブを、simulationを進めずに再読込した。

## ライブMP

全系統を推定扱いにした3駅fixtureでは、接続後の設定OFF/ONと初期構築バリア、
4,179tickの実輸送が成功した（要求4,096tick、ネットワークpauseの到達待ちによる超過）。
確定0・推定1パターンの路線で15人が実乗車・最終配送され、両peerの同じ輸送カウンタと
canonical状態が一致した。参加時、設定切替後、輸送後のmismatchはすべて空。
参加2.538秒、試行123.851秒、NewGRF警告0、network errorなし。

乗り通し修正前c294で実マップの起動直後に接続した試行は、既定900秒の絶対参加期限で切断された。
進捗パケット222件を受けたが、サーバーの初期準備待ちとクライアント再生を合わせて
902.273秒となり、`processing map took too long`が発生した。これは成功試行には含めない。
進捗が来れば期限を延長する変更はしておらず、上限が機能することも確認された。
新旧表の再生を含むサーバー準備の負担が大きく、起動直後の参加は残る制約である。

最終版は最終品質試行の終了セーブを入力にし、サーバーの初期準備完了後に接続して成功した。
ハーネスの`--wait-server-ready`だけを使い、ゲーム側の期限・進捗監視・バリアを変更しない。
サーバー準備待ち665.070秒、接続後の参加399.338秒、試行全体1,119.009秒。
進捗388件、参加前後のStateTicksは3,181,119,581のまま、公開行1,252・保持行3,665、
操作数1,478,098,944を含む全比較項目が一致した。
さらに1,050tick進めた3,181,120,631時点でも全比較項目が一致し、支払い正常、
network errorなし。公開行1,311・保持行3,606、経済期間の旅客配送カウンタ393,934も一致。
最終版の起動準備中接続は再試行していない。準備済みサーバーでの同期成立を、
起動準備中にも900秒以内に参加できる証明とはしない。修正前の準備済み条件も別に成功しており、
その失敗・成功記録は修正前の証跡ディレクトリに保存している。

両実マップ試行で観測された既存NewGRF容量警告を保存している。成功試行では
最終版ではserver/clientそれぞれ26,093行。同一バイナリ・loopback・frame_freq=20での検証で、
あらゆるネットワーク環境やNewGRFの決定性まで保証するものではない。
