# 事前計算旅客ルーティング：共通区間の頻度集約

対象は `codex/passenger-precomputed-completion` の `ffb3dc98db` を基点とする変更。
前回レポートの Phase 4 を実装する。他の残課題をすべて解消したという意味ではない。

追記：初回の `70c654c7aa` では、共通区間の合算頻度と実際の乗車候補が一致していなかった。
以下の初回測定・検証では、この不具合を検出できていない。
修正内容と実乗車による検証は [共通区間Intentの複数系統束縛](passenger-common-section-binding-2026-10-15.md) を参照。

## 区間と実行系統

既存の全停車パターンによるグループを維持し、その上に共通区間の推定を追加する。
乗車可能な各指令から、1周未満の連続した物理停車列を prefix として intern する。
駅、方向、当該 CargoType の NoLoad / NoUnload / 強制降車を照合する。
指令番号、区間外の停車列、所要時間、運行周期は共通区間の識別には含めない。
強制降車駅では延長を止める。交換のない途中駅も照合から削除しない。

複数の全停車パターンが共有する prefix に、区間全体を走る実サービスの発車情報を集める。
同じ始終点だけで異なる経由駅のサービスを束ねることはしない。
同一パターン内の複数の物理乗車指令も、異なる発車イベントとして扱う。

推定した区間待ち時間を、各パターンの具体的な乗車・降車指令を持つ section ride に付ける。
後続修正では、推定に使用した区間全体の適合パターンを、共通の乗車索引キーへ対応付ける。
経路表が返す Intent は従来通り1つの実 OrderListID、incarnation、generation と指令対を保存するが、
これらは区間を識別する代表であり、実際の乗車候補をそのOrderListIDだけに限定しない。
実乗車時には到着系統の具体的な乗車・降車指令へRebindし、従来の実車検証を行う。
同程度のコストの別パターンは既存の構築時代替ラベルにも入れ、取得時には
Packet ID・駅・目的地から決定的に得る既存の sample で選ぶ。

section ride の到着状態には降車辺だけを持たせ、元パターンの車内継続辺とは接続しない。
例えば A-B-C と A-B-C-D-E の共通頻度を使う A→C は、C で降りる。
C→E へ進むには改めて乗車と乗換費用が必要になる。
A→E を直通で選ぶ場合は、A→E 全体を走るパターンの頻度と指令を使用する。

## 発車イベントと待ち時間

既知位相の実車は `base + boarding departure offset` を周期内へ正規化する。
認証済み dispatch slot は dispatch 停車指令から乗車指令へのオフセットを使用する。
dispatch anchor より前の指令は、次の周回に属するオフセットになる。

同じ VehicleID が複数サービスへ現れた場合、区間推定内では最小 OrderListID の所有者だけを使う。
同じ周期・位相の発車列を重複除去し、異なる周期で一致する実発車時刻も1つとして扱う。
台数や定員を発車回数へ掛け合わせない。

65,536イベントの枠に収まる場合は最小公倍数の周期を列挙する。
枠を超える場合は最長の個別周期を観測し、それも超過する極端な周期比では
最短の認証済み発車列の周期へ保守的に戻す。LCM の積も検査する。
発車間隔の最大値の半分を切り上げた値を、区間の待ち時間推定とする。
これは確定出発時刻でも厳密な平均待ち時間でもない。
位相不明・dispatch 未認証の列は架空の等間隔運行へ変換しない。
既知の列がない場合は最短の保守的な1周待ちを使用する。

## 計算量とメモリ

区間照合、イベント集約、待ち時間推定は `Begin()` のグラフ構築時だけに行う。
`Plan()` は公開済みの主・代替ラベルを取得し、具体的なパターン内の系統を選ぶ。
取得に区間、車両、イベントの走査は追加しない。
返す最初の待ち時間もラベルに保持し、取得時に再計算しない。
目的地行の構築・公開は従来の操作予算を使用する。

prefix の一時領域、発車集合のピーク、section ride、到着状態、辺を
ABI に依存しない既存のメモリ envelope に事前計上する。
全パターンが異なる乗車駅を持つ場合や、全体で1パターンだけの場合は区間列挙を省く。
最悪時には各パターンの停車数の二乗に比例する構築時間・領域が必要になる。
これは通常取得の負荷と引き換えに許容する構築時コストであり、極端な入力では
既存の16 GiB共通メモリ枠により拒否され得る。
グラフ準備そのものの完全な時間分割は、今回の変更には含めない。

## 保存と決定性

JPSD と `passenger_periodic` feature を v8 に更新する。
現表・保持中の旧表それぞれのグラフ方式を保存する。
v4〜7 の構築カーソルは従来グラフを使用して正確に再生し、次の決定的な更新で新方式へ移る。
v4/v5 の行公開操作の補正も維持する。移行中は旧方式・新方式の両入力と方式を保存する。
同じ入力・操作カーソルからの再生結果は、処理 slice と問い合わせ履歴に依存しない。
発車推定は整数演算を使い、壁時計やローカルな空きメモリを判断に使わない。

CargoPacket の保存フィールド、支払・運賃計算、実車の乗降検証は変更しない。
乗車時は従来の指令、施設、容量、予約、禁止条件と世代検証を経由する。

## 検証

MSVC x64 Release、assert ON、LTO OFF、Passenger Benchmark OFF を使用する。
事前計算関連は **30ケース・43,751アサーション成功**。
全CTestは初回632/636成功。残る4件は制限下のWindowsフォント読込警告が
期待出力へ混入して失敗し、制限を外した同じバイナリの再実行では4/4成功した。
製品コードや回帰の期待出力を変更して通過させてはいない。
回帰には短区間折返し、異なる周期、重複車両・発車、dispatch anchor、位相不明、
NoLoad / NoUnload / 強制降車 / 途中通過 / 逆方向、周回境界と指令番号の違いを含む。
旧カーソルの移行、旧方式を保持した更新、構築途中の保存復元と slice サイズの独立性を検証する。

合成CPU計測の axis 4 は、周期の異なる長短2パターンの共通区間を持ち、
実車を256〜8,192台へ増やす。同位相の複製イベントを除去した同じ経路表に対する取得を測定する。
実マップの長時間運転と新コードによる実server/client途中参加は、この合成回帰の代用にはならない。

主要配列は各条件531,044 bytes。入力・一時領域を含む保守的envelopeは

全合成試験のprocess CPUは3.15625秒、OS peak working setは56,754,176 bytesであり、
表単体や通常simulation区間の値ではない。他のホスト処理の影響は排除していない。
