# CargoDistの系統コスト・乗り換えペナルティの修正記録

対象は `jgrpp-ya` の `e08d3c31df`。`3a7ffff8ab` で取り込まれた機能を維持した修正である。系統コスト設定、乗り換えペナルティ、長編成の手前端停車、時刻表ベースの旅客乗り換えを削除していない。

## 確認した問題と修正

| 問題・再現条件 | 修正と検証 |
| --- | --- |
| Bへの安い到着は系統1、少し高い到着は系統2、その先のB→Dは系統2。駅ごとの最良経路だけでは後者が失われる。 | 非ゼロペナルティでは `(駅, 到着系統・車種, 残容量の有無)` ごとに候補を持つ。距離優先・容量優先の両段階で、B自身には安い経路、Dには系統2の継続経路を割り当てるテストが通る。 |
| Aだけのリンク→AとBの共有リンク→Bだけのリンクでは、隣接リンクの共通系統だけを見ると実際の乗り換えが消える。 | 遷移時に実際に選んだ到着・出発系統を比較する。共有リンク内でAからBへ無料で切り替える扱いを解消した。 |
| 残容量のある高い経路が、安い容量不足の経路を途中駅で消してしまい、さらに先の容量不足リンクで経路選択が逆転する。 | 残容量あり・なしを別のラベルにする。この逆転の回帰テストを追加した。 |
| `Path::Fork()`、両Annotation、経路探索の加算が32bit。リンクコストが大きいと経路全体が折り返す。 | コストと比較値を64bitへ変更し、到達不能を `UINT64_MAX`、有効な最大値を `UINT64_MAX - 1` に分けた。加算は有効な最大値へ飽和する。 |
| 容量比の負の分子が、符号なしの分母によって正の値として計算される。容量倍率にも32bit乗算が残る。 | 容量比は符号付き64bitで計算し、容量倍率と残容量の差も拡張・クランプした。負の容量比を検証した。 |
| OrderListを削除後、同じpool IDを別系統が再利用すると、古いリンク記録が一致する。 | OrderListに保存される世代番号を追加し、IDと世代の組で照合する。新規ジョブ作成時に主スレッドで無効化し、実行中ジョブは不変のスナップショットを使う。 |
| OrderBackupが非共有指令のコスト設定を保存していない。 | 作成・復元とBKORの名前付き保存項目へ倍率・追加コストを追加した。元の指令を削除後の復元と、共有指令の生存車両を使う復元を検証した。 |
| 16件の系統上限で先に記録された系統が消え、乗り換え判定が変わる。 | OrderList poolの上限64,000件まで保持する。通常の更新は系統ID順の配列を二分探索し、新規項目だけ挿入する。98系統を保持するテストが通る。 |
| ゲーム中のコスト編集が、次の車両のリンク観測まで反映されない。 | 新規ジョブのスナップショット作成時に現在の設定を同期する。走行中のジョブの設定・観測値は変えない。 |
| LinkGraph統合で64bitの所要時間合計を32bitの `Scale()` へ渡して切り詰める。 | 型を保持する乗除算へ変更し、商と余りに分けてオーバーフローを防ぐ。圧縮・統合後にも32系統と所要時間100,000 ticksを保持するテストが通る。容量観測の加算も飽和させた。 |
| 不正な車種、ノード、重複、件数、設定、容量・日時をロードできる。 | 下記の検証・正規化を追加し、実行ファイルのセーブ読み込みで26種類の不正データを拒否した。 |

## 探索方式と正確性の範囲

状態は、その駅に入るリンクで観測された系統だけに作る。全駅と全OrderListの直積は確保しない。同じリンクの複数系統はそれぞれの遷移として展開し、到着状態を更新する。残容量の有無も分離する。系統不明のリンクには不明状態を一つ作る。

距離優先探索では、この状態グラフ上の非負のリンクコストと乗り換えコストについて最短のラベルを求める。残容量のある経路を優先する既存の順序を保ち、その分類内で距離を比較する。経路復元には不変のラベルIDと親IDを用いる。Bの最良の到着経路が更新されても、既に選んだDへの経路の親を置き換えない。必要な目的地とその祖先だけをPathへ復元する。

ゼロペナルティでは既存の駅単位の探索を使う。両段階で未配分需要のない出発駅を省くが、需要のある駅の探索・割り当て順序は変えない。中立の系統設定100%・0日で、通常の整数範囲にある入力の経路コストは従来と同じである。オーバーフローや負の容量比による誤動作は修正対象とする。

以下は正確な系統別輸送計画とは扱わない。

- リンクの倍率・追加コストは、取り込まれた仕様どおり容量加重平均である。普通・特急それぞれの実コストを別々に最適化するものではない。
- リンク容量と最終FlowStatは駅間で集計される。系統のラベルを増やしても同じ物理リンクの容量は共用し、系統数倍の容量を作らない。一方、各系統の観測容量を独立した割り当て上限としては使わない。少容量の共通系統にも継続候補があり、集計容量分の継続可能性は楽観的な推定となる。
- 容量優先段階の `min(残容量) / min(容量)` は経路延長によって順位が逆転し得る。従来の容量割り当てヒューリスティックを保持し、厳密な容量比最適化や多目的Pareto探索とはしない。
- 最終MCFは系統IDを保持しない駅/viaフローへの投影と循環除去を行う。状態グラフ上の最短のwalkと、最終的な循環のないフローを同一の最適化結果とは保証しない。特に、同種乗り換えコストが異種乗り換え2回分より高い設定や、不明情報による無料遷移では、迂回・循環によってペナルティを回避する余地がある。
- メタデータが欠落したリンクの遷移は、従来どおりペナルティ0とする。実際の乗り換えコストの厳密な復元は保証しない。
- 64bit飽和に達した有効コストは到達不能とは区別できるが、それ以上の値同士の大小は区別できない。

容量優先探索では、出発駅ごとのフローが非循環であることをトポロジカルソートで確認する。非循環なら、全ての経路延長で親をたどる循環チェックを省く。循環が残る入力では親チェーンのチェックを維持する。循環によって容量比が改善する入力の回帰テストも通る。

MCFの初回割り当てでの例外的な過負荷と、第2段階で残余需要を既存フローへ配分する過負荷許容は維持した。全体を新しい系統単位の多品種流最適化に置き換えたものではない。既存の旅客時刻表比較、座席予測、保持via、CargoPacket処理は変更していない。

## IDの寿命と保存互換性

系統削除のたびに全LinkGraphを走査しない。削除後の記録は世代不一致によって使用対象外となり、新規ジョブのスナップショット、既存の期限切れ処理、セーブ出力時のフィルタで取り除く。再利用IDへの新しい観測は、そのIDの古い容量を引き継がない。

新しい名前付き項目はOrderListの世代、EdgeRouteの世代、LGRSの採番カウンター、BKORのコスト設定である。元の `edge_routes` 項目を並べ替えたり、`linkgraph_route_penalty` の拡張バージョン1を変更したりしていない。旧非テーブル形式には追加項目を入れていない。

採番カウンターは削除済みの系統も含めて保存する。指令保存GUIなどのpool外OrderListには採番せず、GUI操作が同期状態を変えないようにする。読み込みで作られた一時的な採番は破棄し、保存カウンターと生存OrderListの最大世代から復元する。新しいゲームではpool初期化時にリセットする。これにより、ネットワーク参加後の新規系統でサーバーとクライアントの採番が食い違うことを避ける。ワーカーを開始する前に、ロードしたグラフとジョブの世代を照合する。

公開済み `jgrpp-ya-0.73.3+2` 形式の記録には世代がない。そこに既に再利用されたIDが混ざっているかは判定できないため、古い系統観測キャッシュを破棄し、運行車両から再観測する。保存されたOrderListの倍率・追加コスト、リンク本体、需要・貨物は維持する。再観測まで系統不明扱いとなる点は移行上の制限である。新形式の一致する世代の記録は再ロードでも保持する。

通常ゲームのBKORは既存仕様に従ってセーブ出力対象外・ロード後削除である。追加項目はサーバーからクライアントへ渡すBKORにも含まれる。今回は実際のBKORテーブル読み込みと、共有・非共有のバックアップ生成/復元を検証した。実ネットワーク接続でのBKOR往復とマルチプレイのリプレイは未実施である。

## セーブの検証と資源上限

名前付きテーブルの `edge_routes` では以下をロード前・ロード中に検証する。

- 車種0～3、OrderListID 0～63,999、倍率10～1,000%、追加0～365日、非ゼロ観測容量、有効日付。
- from/toがグラフ内の異なるノードで、実際のリンクが存在すること。同じリンク・系統の重複を拒否する。
- リンクの宛先・重複、容量0、使用量が容量を超える値、平均所要時間が32bit上限を超える値、ノードとリンクの無効な日時を拒否する。
- OrderListとBKORのコスト設定、OrderList世代と採番カウンターの範囲を検証する。無効な車種によるビットシフトは実行時にも防ぐ。
- 表現可能だが現在日付より未来の更新日時は、ワーカー開始前に現在日付へ正規化する。削除されたID・世代不一致・旧形式の世代なし記録も使用前に除去する。

LGRPとLGRJそれぞれに、合計1,048,576ノード、1,048,576リンク、4,194,304系統記録のロード予算を置いた。各配列の件数も確保前に検証する。重複検出の補助配列は予算内であり、計算量は記録数に対してO(R log R)。この上限を超える正当な極端に大きいセーブも拒否する。

これらは追加の系統テーブルと現在のテーブル形式の検証であり、OpenTTDの全ての旧セーブ形式・全チャンクの包括的な破損検証ではない。

## 長編成の停車位置

`train_cmd.cpp` の既存実装を確認し、実Station・Train・線路タイルを使う関数単位の回帰テストを追加した。ホーム2タイルに対する長編成で、先頭側のホーム外停車を維持する。

前進、逆向き、連接単位、Dual-headed Engineの車両構造、折り返し時のフラグリセット、32両、最後の移動単位がホームに入らないケース、Realistic Brakingフラグの停止位置を検証した。通常の幾何学的な予測と実停止目標が一致し、先頭のホーム外車両に `BeyondPlatformEnd`、乗降側の車両にその解除状態が設定される。乗降処理も既存の同フラグ判定を使うことを確認した。

ホーム直後の行き止まり・非互換線路・一方通行信号では、停止位置計算が既存の移動制約に応じて短縮される。予約済み線路は駅の幾何学的な目標を変更せず、予約と信号への服従は既存のTrainController/制動処理が受け持つ。

今回のテストで修正を要する停車位置の不具合は確認できず、`train_cmd.cpp`、Through Loading、SSE4描画は変更していない。実際に毎tick走行させた停止・乗降、対向列車との競合、赤信号待ち、ブレーキ物理全体についての実ゲームのリプレイは未実施である。関数単位の予測比較を、障害物まで含む全制動予測の一致とは扱わない。

## CPU・メモリ

比較対象の「0」は修正後コード内の駅単位探索であり、`e08d3c3` の旧実行ファイルとの比較ではない。同一の合成グラフと中立/加重系統設定を使い、ペナルティだけを0または非ゼロとした。連続駅間リンクは2系統を共有し、8駅先へのリンクを一つ追加する。2,048駅で4,087リンク、8,192駅で16,375リンクとなる。

8,192駅の状態数高水位は32,765。距離段階のラベル16,444・queue 95・scratch payload概算2.44 MiB、容量段階のラベル24,486・queue 8,159・概算3.48 MiBだった。概算はアロケータの管理情報などを含まず、プロセスRSSとは別の値である。現在のMSVC x64ではPathは48 bytes、EdgeRouteは24 bytes。

系統状態のトポロジーは各MCF段階で一度作って再利用し、各出発駅の探索ラベルは順次解放する。追加状態数は観測された駅・到着系統の組数に比例する。ただし緩和候補数は、駅ごとの到着系統と出発リンクの系統数の組み合わせで増える。全ての組を列挙しても16件で切り捨てることはしない。改善ラベルの数と保持Pathの数も入力・需要に依存する。

多系統が密集する実マップ、8,192駅全駅を発駅とする全対全需要、多数の同時ジョブ、非常に深い経路についての処理時間上限は保証しない。既存の再帰的なフロー・循環処理も残る。今回の結果は合成グラフでの実測であり、全国規模の運行中セーブでのフレーム時間・完了時間の保証ではない。
