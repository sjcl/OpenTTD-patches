# 旅客表のロード再生とMP途中参加

実装はc702dd4a11（表再生）とd0d2b6023e（参加後の追い付き）。この変更は、[前回](passenger-precomputed-completion-2026-10-15.md)に実サーバーで失敗した巨大表のロード再生を対象とする。全Phaseの完了を意味しない。

## 実装

FinishLoadはグラフと保存カーソルを準備し、MPクライアントでは行と探索フロンティアの再生をStepLoadに委ねる。1回の作業上限は既存の65,536操作。通信ループの約8msのソフト上限で呼び出しを区切り、通常の受信・送信・入力処理に戻る。古い完成世代の再生と、新世代の保存カーソルまでの再生の両方を分割する。グラフ構築のBegin自体は従来どおり同期処理である。

再生中のカーソルはローカル作業状態であり、保存対象の構築カーソルを進めない。保存データ、公開済み行、旧行の解放位置を復元し終えるまでMAP_OKを送らず、コマンド実行・StateTicks・クライアントのネットワークフレームを進めない。旧v4/v5形式は、再生中の保存にも元の形式を保持し、再生完了時に公開操作数を移行する。不正なカーソルは参加失敗として処理し、不完全な状態の緊急保存を抑止する。

ClientMapProgress / ServerMapProgressを同じ版のプロトコルに追加した。クライアントは約1秒おきに完了した再生操作数を送り、サーバーは次を確認する。

- マップ送信を終え、MAP_OKを受ける前の状態である。
- 直前より操作数が増加している。
- 実際に送信した保存スナップショットから求めた再生作業上限を超えていない。

検証済みの進捗だけが既存の参加待ち期限を更新する。返答も通常の受信ループで処理する。進捗通知はゲームフレームのACKとは別で、参加待ちの一時停止を解除しない。ネットワークのmax_join_time、max_lag_time、その他のタイムアウト値は変更していない。同じ操作数の通知を繰り返すことは許可しない。

参加後のクライアントの追い付きループも約8msのソフト上限で分割した。実行済みフレームのACKを送信し、次の受信へ戻れるようにする。一定周期の描画ドライバーで遅れを回復できるよう、追い付き対象が残る場合は少なくとも2フレームを処理してから時間判定する。未実行フレームをACKしたり、サーバーの許可範囲を超えて進めたりしない。

## 実サーバー・クライアント検証

Windows x64、assert有効のRelease、専用サーバーとnull描画のクライアントを別プロセスで起動した。接続先は127.0.0.1。pause_on_join=true、min_active_clients=0、ネットワークタイムアウトは既定値。4,636駅・687パターン・44,080状態・99,090辺の既存実マップを使用する。

比較対象は次の通り。

- 全CargoPacketの人数、OD、経由地、Routing Mode、Intent、世代、再試行時刻、支払い関連フィールド。
- 駅・車両ごとのPacket IDと所属順、予約数、Keep/Load/Transfer/Deliverの人数、積載状態、停車中車両の順番、車両位置と注文位置。
- 遅延支払い情報と整合性。
- 経路DBの保存バイト列全体のdigest、公開世代、旧新の公開行数、決定的な操作数。
- 同じStateTicksでの輸送後の状態と、通常のMP同期チェック。

FNV-1a digestは同一状態の回帰検査に用い、暗号学的な証明とは扱わない。公開行の経路内容は分割幅を変える単体テストでも照合する。

長時間の実輸送では、完成済み1,051 tick、初期構築途中1,060 tick、更新途中1,078 tickで同一StateTicksの全照合項目が一致し、desync・切断はなかった。初期構築ケースでは既知ODの乗車292,733人・最終配送41,225人、更新ケースでは乗車177,660人・最終配送39,445人の実移動カウンタも一致した。

長時間試験は順次修正中のバイナリで行った。完成済みは表再生修正、更新途中はc702dd4a11、初期構築途中は追い付き分割追加後・最小2フレーム調整前である。最終のd0d2b6023eでも3状態の参加・実輸送を再検査し、バイナリSHA-256を各結果に記録した。

再生操作数は順に1,225,505,375、67,108,864、1,292,586,678。再生中のStateTicksとクライアントのフレームは不変で、約1秒ごとの双方向進捗通信を継続した。最大時間は再生中と判定したGameLoopの測定値であり、ダウンロード、一般ロード、グラフBeginの段階を含まない。参加所要時間はこれらを含む経過時間で、CPU時間とは別である。

最終試験のピークworking setは、完成済みがサーバー5,475,295,232／クライアント4,645,527,552 bytes、初期構築途中が2,391,756,800／1,504,944,128 bytes、更新途中が5,496,963,072／4,657,160,192 bytesだった。ルーティングの論理メモリ上限は変更していない。

再生停止の対照試験では、構築途中のクライアントが最初の実進捗を送った直後に、この試験のクライアントプロセスだけを一時停止した。約15.47秒後、既定の500 tickでサーバーが切断した。進捗のない接続を無期限に維持する変更ではない。試験後はプロセスを再開して回収した。

検査過程の失敗も保存する。初期構築の最初の輸送後比較はサーバーとクライアントで16 tick違っていたため、同一時刻の不一致とは判定できない。検査を「一定秒待つ」方式から、双方の停止コマンド適用とStateTicks一致を確認する方式へ直した。別の試験を同時起動した試行では、参加後のクライアントが一般タイムアウトになった。このログを残し、長い追い付き処理の通信占有も修正した。修正後の長時間試験と最終再検査は順番に実行した。

再生停止試験の初回は、サーバーが500 tickで切断した行をstdoutに出していたのに、検査がstderrだけを探して失敗判定になった。この試行も残し、出力先を修正して上記の最終試験を再実行した。ログ末尾の検査用プロセス終了による切断表示は、照合・通信エラー判定を終えた後の回収処理に属する。

## 検査と根拠

分割再生の24テスト、24,338 assertionが成功。分割幅1・19・65,536で、3状態の保存バイト列、公開行、経路結果、再生後の通常構築進捗が一致する。不正カーソルの非同期エラーと、旧形式の再生中保存・移行も検査する。

測定用TUの参照を外し、OPTION_PASSENGER_BENCHMARK=OFFに戻した通常製品を再ビルドし、全630件のCTestが成功した（93.24秒）。初回の全回帰では、新しい2パケット名が既存の全数検査に未登録だった1件だけが失敗した。名前検査に両方を加え、全630件を再実行して成功を確認した。実行時コードの変更や検査の削除は行っていない。

## 測定用コードと再現

製品に検査用のファイル監視や経路変更は追加しない。utils/passenger_precomputed_join_prepare.pyはビルドディレクトリ内のコピーTUに、状態検査・再生ループ測定・ローカル検査要求の読出し・Windows標準入出力の設定を加える。ネットワーク処理と経路再生は製品コードをそのまま使う。

    cmake -S . -B <build> -DOPTION_PASSENGER_BENCHMARK=ON
    python utils/passenger_precomputed_join_prepare.py <source> <build> <revision>
    cmake --build <build> --config Release --target openttd
    python utils/passenger_precomputed_join.py <exe> <package> <complete.sav> <complete-output> <lang>
    python utils/passenger_precomputed_join.py <exe> <package> <legacy-mode.sav> <initial-output> <lang> --initial-build
    python utils/passenger_precomputed_join.py <exe> <package> <replacement.sav> <replacement-output> <lang>
    python utils/passenger_precomputed_join.py <exe> <package> <complete.sav> <stalled-output> <lang> --stall --ticks 0

初期構築ケースは、旧方式のMP利用可能な実セーブで設定を有効にし、停止中に64Mi操作だけ行う。旧行を持たない最初の構築を途中で止めてから参加させる。更新ケースは、前回の転送ペナルティ20→17の通常更新を1,024 tick進めた実セーブを使用する。各試験の入力SHA-256と設定コマンドを保存する。

元の修復入力はError停止の状態で保存されており、専用サーバーが通常の検証でMP利用を拒否する。この制限を回避する変更は行わず、既存の正常な実輸送後セーブを使う。

実マップのNewGRF「JP+ Multiple Units」の既存の車両容量変更警告は残る。測定ビルドの既存のunpauseにはError停止解除の機能があり、開始時の明示的な停止解除に使われる。輸送中の警告を隠さず、ネットワーク切断・desyncとは別に件数とログを記録する。この試験だけでNewGRF全般のMP安全性は保証しない。

検査後はCMakeを再configureし、コピーTUを外してOPTION_PASSENGER_BENCHMARK=OFFの通常製品へ戻す。実セーブ・NewGRF・実行ファイル・秘密鍵を含み得る終了時設定ファイルはGitに追加しない。

## 範囲

この変更は表再生によるMP途中参加の停止を直すもので、通常tickの構築作業量、経路コスト、候補選択、メモリの論理上限を変更しない。非停止での途中参加、複数クライアントの同時参加、全種類のダイヤ編集、長時間の輸送品質の評価は別の検証対象である。Phase 2・4等の前回の未完了項目も引き続き残る。
