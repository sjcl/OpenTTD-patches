# MP起動準備待ちとクライアント参加期限の分離

起動準備中からの実マップ参加と、その後1,071tickの同期に成功した。
サーバー準備待ち660.853秒・クライアント参加295.171秒を別に計時し、合算900秒を超えても
各予算内なら参加できる。再生を停止したクライアントは既定の無活動監視で切断した。

基点は `674d5ab12e`。従来の実マップ記録では、認証後にサーバー準備を約665秒待ち、
その後のクライアント読み込み・表再生に約399秒かかる。両者を同じ900秒に含めると、
正常な参加が途中で期限切れになり得た。この修正はその計時を分離する。
実装コミットは `5583fc2feb`、ライブ計測の補助は `b661c7822c`。

## 計時と上限

`max_join_time_total` の既定900秒を変更せず、接続ごとに次の二つの累積時間を持つ。

- サーバー準備待ち：マップ要求がMapWaitにあり、サーバー自身の旅客DBが実際に
  初期表・グラフ・保存表を準備していて、マップ送信を開始できない時間。
- クライアント参加時間：認証完了からの経過時間から、上記の待ちを引いた時間。
  通常のマップ待ち行列、ダウンロード、読み込み・再生、参加後の追い付きを含む。

それぞれが同じ設定値に達すると切断する。計時モデル上、認証後の合計上限は
既定で1,800秒未満であり、期限判定は通信ループで行う。サーバー準備自体が止まっても、
その待ちを無制限には除外しない。認証前のタイムアウトも維持する。

開始時刻と二つの累積予算は、再生開始・進捗通知・待ち行列の移行でリセットしない。
繰り返しサーバー準備待ちに戻っても、待ちの合計で上限を検査する。
他のpeerが準備完了を返さないだけの場合、サーバーのローカル準備が終われば除外しない。
Map/DoneMap/PreActiveではクライアント自身の作業が可能なので、その時間も除外しない。
接続済みpeerの既存準備バリアの期限は変更しない。

除外状態はSendMapとNetworkServer_Tickがサーバーのローカル状態から設定する。
クライアントの申告、frame ACK、進捗パケット、壁時計による経路表公開順からは決めない。
進捗は従来どおり単調増加・送信snapshotの作業上限内・burst/rate上限内で検査し、
更新できるのは再生無活動の監視だけである。既定500tickの無活動監視も維持する。

ワイヤ形式・セーブ形式・旅客経路の費用や公開順は変更しない。サーバーのdebugログに、
MAP_OK時点の `server_preparation_ms` と `client_join_ms` を出し、計時を診断できるようにした。

## 検証方法

単体回帰では、665秒のサーバー待ち後の399秒参加を許可し、その後のクライアント累積
900秒で失効すること、進捗・Start/BeginReplayの再呼出しで失効を取り消せないことを検査する。
また、サーバー待ちの繰り返しで累積900秒を超えるケース、サーバーがずっと準備中のケース、
別クライアントと通常待ち行列への除外時間の漏れがないことも検査する。

ライブ試験は製品のネットワーク処理をそのまま使う。計測用コピーTUは状態digestと
検査要求の受付だけを追加し、期限・進捗・経路再生を変更しない。
起動中接続ではハーネスの `--wait-server-ready` を指定せず、接続後に両段階を通過させる。
`--observe-timeout` は検査プログラムの観察時間であり、ゲームの期限を変更しない。

期限回帰は5ケース・2,393アサーション成功。小規模全推定fixtureでは、通常参加と
設定OFF/ON後のバリア、4,179tickの実輸送が成功し、参加・切替・輸送後の全比較項目が
一致した。接続からの観測時間2.550秒、MAP_OK時のサーバー準備待ち0秒・クライアント
予算消費0.189秒、試行全体123.718秒。要求4,096tickからの超過はネットワークpauseの
到達待ちによる。NewGRF警告0、network errorなし。

### 起動準備中からの実マップ参加

前の準備済みサーバー試験と同じ品質終了セーブ
（SHA-256 `306a8d3094c406286ff1dd3249f1726bf9d10e230ead593eacdd91efc43ac629`）を使った。
サーバーがframe 0で初期表を準備中に接続し、`--wait-server-ready` は使っていない。
既定 `max_join_time_total=900` を実行時設定出力でも確認した。

| 項目 | 結果 |
|---|---:|
| MAP_OK時のサーバー準備待ち（サーバー計測） | 660.853秒 |
| 同・クライアント参加予算消費 | 295.171秒 |
| 同・両予算の合計 | 956.024秒 |
| 接続開始から結果を観測するまで（ハーネス） | 958.562秒 |
| 参加後の実輸送 | 1,071 StateTicks |
| 参加時 / 輸送後のcanonical不一致 | 0 / 0 |
| 再生進捗パケット | 290件 |
| 試行全体 | 1,010.170秒 |

以前の合算900秒を超えて参加が成功した。二つのサーバー計測値は認証後からMAP_OKまでの
計時で、ハーネスの接続開始・snapshot観測とは範囲が異なる。クライアント時間が前の399秒から
短くなったことを、この期限変更による再生高速化とは主張しない。反復による時間分布は未測定。

サーバーの準備前snapshotはStateTicks 3,181,119,581、公開行0・保持行0だった。
参加時も同じStateTicksのまま、公開行1,252・保持行3,665・操作数1,478,098,944まで
復元され、Packet、経路DB、支払い、予約・所有権・積載、表進捗、経済カウンタが一致した。
クライアント再生は24,385ループで、StateTicksとframeは開始・終了とも不変。
測定した最大GameLoopは80.850ms。既存の約8msはソフト上限であり、一般ロードや
原子的な構築処理を含めた全ループの厳密な上限ではない。再生処理自体は変更していない。

さらに3,181,120,652まで1,071tick進めても全項目が一致した。
公開行1,312・保持行3,605・操作数1,548,288,000、旅客配送の経済期間カウンタ396,143も一致。
要求1,024tickからの超過はpauseの到達待ちによる。支払い正常、network errorなし。
既存NewGRF容量警告はserver/clientそれぞれ26,137行を保存した。

### 再生停止の対照試験

旧Legacy入力（SHA-256 `cc73ec5d569d9582f96e42aae67d77022ac085e64683db36394930f3a24e6b68`）を
`--initial-build` で初期構築し、今回も準備中から接続した。クライアントの最初の実再生進捗を
サーバーが受信した後、この試験のクライアントプロセスだけを一時停止した。
停止から13.686秒後に、既定500tickの無活動監視によって切断された。
計測の開始はプロセス停止時点なので、前の進捗受信からの経過時間とは異なる。
進捗を偽装して接続を保つ処理はない。試験後はクライアントを再開して回収した。
試行全体590.099秒、既存NewGRF警告は両peerそれぞれ5,601行。
これは参加成功を目的としない負の対照で、切断が期待結果である。

進捗を増やし続ける場合にも900秒で失効する検査、累積サーバー待ち900秒で失効する検査は、
単体テストの人工時計で実施した。実回線で900秒分の偽進捗を送る攻撃試験は行っていない。

## 適用範囲

別枠は接続ごとの累積上限であり、任意に長いサーバー準備やクライアント再生を許可しない。
サーバー準備待ちだけで設定値に達する場合も切断する。認証前・再生無活動・接続済みpeerの
バリア期限はそれぞれ従来どおりで、他クライアントを待つだけの時間も除外しない。
二つの予算は同じ既存設定値を使い、個別の新設定は追加していない。
検証は同一バイナリ・loopback・frame_freq=20での単発試行である。
すべての回線・機器・NewGRFで900秒以内に処理できる保証ではない。
