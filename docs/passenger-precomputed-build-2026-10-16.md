# 旅客経路表の構築高速化

scalar SoA・RangeEdge・安定CSR・予算付きブロック初期化・ノードバッチ・Radixを採用する。
採用構成を固定した時点で `667e154816` をcommit・pushし、その後に最終検証を行った。
同じ固定サービス入力の全経路表構築は133.6秒から60.3秒へ54.9%短縮、約2.22倍になった。
通常tick全体の平均には増加が観測されており、不悪化の条件は現時点では未確認である。

基点は最新 `sjcl/jgrpp-ya` の `902997e6314e018a08c4b92ec0083b040790005f`。
作業ブランチは `perf/passenger-precomputed-table-build`。
費用、待ち時間推定係数、乗降条件、分散条件、Work Budgetは変更しない。
完成表のLabel形式は48 byte、costはint64、legsはuint32のままである。

## 実装

変更は独立コミットに分けた。

| 変更 | 内容 |
|---|---|
| 通過Occurrenceの縮約 | 実グラフの入出次数が各1で、Board/Alight/forced/seedの参照がないarrival/departureを削除。距離・費用・不確実性を元の辺から合算する |
| SoA | cost/legsと冷たいmetadataを分離し、優先度が改善した場合だけmetadataをコピーする |
| 逆向きCSR | 各状態の元の辺順を保ったままEdgeを直接連続配置する |
| 辺のhot/cold分離 | from/cost/leg delta/range IDを連続配列へ置き、採用時だけoccurrence/distance/uncertainty/kindを読む |
| RangeEdge | Board/Sectionの基底駅と連続waiting stateを1 descriptorへ圧縮。単独memberのprevious pattern除外を保存し、基底駅→元のstate順に展開する |
| 作業領域の再利用 | 全状態のcost/legsを初期化し、到達不能な旧metadataは読み出さない。世代番号や保存済み進捗の解釈は追加しない |
| ブロック初期化 | 許可されたWorkに相当するcost/legsのprefixだけをresize/fillする |
| ノード単位バッチ | 同一toのCSR要素を連続走査し、範囲内offsetとCSR cursorで途中再開する |
| seed索引 | StationID別に、元のOccurrence順の降車seedを作る |
| Radix Heap | costだけを単調キーとし、同一cost内は(legs,state)のbinary heapで正確に順序を保つ |
| 代替候補のmetadata | 優先度・採否条件の検査を先に行い、採用する候補だけLabelへ実体化する |

主なコミットは、旧実装比較`8b5b9a65ba`、通過縮約と旧再生`9432f2c209`、
Label SoA `37ae3d0aac`、安定CSR `2806b2dd31`、作業領域再利用`edd103846e`、
seed索引`da1271ce44`、同点回帰と償却条件`c88af3cd87`、Radix `f85c88d6ed`、
代替metadata `d289dadf52`、辺hot/cold `4d98df0ac6`、Range `5fb8a07385`、
ブロック初期化`3601641832`、ノードバッチ`7abdbaa1b4`、v10再生`7f8e4fc878`、
source優先度の保持`bf2511a21d`、Range後の縮約条件`3429f283b2`、
非採用方式の比較ツール`d324c16271`である。

元のOccurrenceとOrderの対応、共通区間束縛、SectionRide、section landingは残す。
状態番号は削除後も元の相対順位を保つ。縮約前に全合成辺のint64加算を検査し、
表現できない場合は縮約しない。距離は元の非負距離を飽和加算し、両端駅から再計算しない。

小さい通過人口では、削減操作数の上界が準備の2回の辺走査を償却しない場合、
元のグラフを使う。この選択は凍結入力のサイズだけに依存する。
Range版では、仮想辺数を基準に、削減Workの上界が1%に届くことも条件にする。
実マップの通過候補は20/17,445件だったため、最終版ではこの縮約を行わない。
合成の500系統では580〜658状態、同数の辺を削減した。

## 採用しなかった方式

Alight-onlyのdeparture除去は、費用とlegsが一致しても元の候補到着順を変える。
回帰例は A→B→C→X の区間時間101、B→Dの150、C→Dの100、全dwell/乗換時間0、
BはNoLoadである。A→Dの費用はどちらも615、乗車回数は2だが、元の処理ではBで降車し
乗車時間251となる。departureを短絡するとC継続候補が先に入り、降車駅と乗車時間が変わる。
このためarrival/departureを残す。回帰テストがこの同点選択を固定する。

Indexed Heapは正確に動き、stale popを全て除去したが、この実マップではRadixより遅い。
製品コードには含めず、比較用実装を `utils/passenger_table_build_heaps.h` に隔離した。
製品の整数幅は圧縮しない。入力ごとに上限を証明するpacked keyも比較したが、採用する速度上の理由がなかった。

SectionRideは全候補を元の順に検査する。最安1件への集約や候補数上限は導入しない。
強く連結した実マップでは到達可能landingによる索引の除外効果が小さく、全候補走査が残る。
安全なcost先行検査でmetadataの繰り返しコピーだけを減らした。

## 固定入力と計測方法

実マップは既存の品質試行終了セーブで、SHA-256は
`306a8d3094c406286ff1dd3249f1726bf9d10e230ead593eacdd91efc43ac629`。
JPSD v9の公開サービスと、同じセーブの駅座標を固定した。864サービス、17,445 Occurrence、
4,917旅客駅、140,481 SectionRideを対象とする。マップは16,384×4,096。
物理駅は5,008。時刻・乗降mask・推定品質・車両位相・容量を変更しない。

MSVC x64 Release、assert ON、LTO OFF。
旧クラスは基点コミットから別名の独立TUへ生成し、製品候補と同じ実行ファイルで比較する。
このnative比較は同一のDLL CRT・dedicated構成内なので、旧新のビルド条件が一致する。
計測TUは明示的なCMake includeでのみ追加し、通常の製品・テストにはリンクしない。
診断付きの計数試行と、カウンター更新をコンパイル除去する時間試行を分離する。
壁時計・allocator容量・物理メモリ残量は経路の採否や公開条件に使わない。
他アプリの負荷は完全には排除できないので単発の小差を確定的な改善とは扱わない。

例外入力は既存のpacked要素を辞書順を保ったwide keyへ戻して続行する。

SIMDのブロック版も再評価した結果を次節に示す。
これらの段階は同じ実行ファイルで順番に測った値で、CPUの変動による小差を含む。

5,664,861,629へ0.014%減るだけだった。永続Label領域は変わらず、追加速度は測定ばらつき内だった。
このため小さな削減をRangeの物理辺数だけで有利と判定せず、上記の凍結サイズ条件を追加する。

### 最終版の性能

最終のカウンターなし時間試行、通常tick、保存復元・MPの結果は、
`measurements/passenger-precomputed-build-2026-10-16` の生記録とsummaryに対応する。

採用構成のカウンターなし試行は、旧版が準備3.863秒＋表処理129.725秒、
新版が準備3.959秒＋表処理56.323秒だった。合計は約133.6秒から60.3秒へ55%短縮。
同じ試行のブロックSIMDは57.658秒、世代管理は65.851秒で、どちらも採用しない。
この試行では全3方式のLabel・共通区間キーが一致し、284,010,453アサーション成功した。
SIMDは4つのint64 costを比較し、同costのlaneだけuint32 legsをint64へ拡張して比較する。
更新metadataとheap挿入は元のstate順に行う。CPU/OSのAVX2対応を実行時に確認し、
非対応時とscalar強制設定では同じscalar maskへ戻る。実験TUにのみ含める。
世代番号方式もWork課金を残したが、初期化より各緩和の世代検査が重くなった。

計数試行の初版はRangeのcold materializationもrelaxationsへ加算していた。
`integrated-counted-matrix/result.json` はraw値を`recorded_relaxations`へ残し、
別計数のLabel materialization分を引いて仮想辺数へ補正している。raw.logは変更していない。
計測ツールを修正し、最終製品構成でも独立して再検査した。

最終構成の独立した計数・全Plan比較で、補正なしでも以下の数が一致した。

## 正確性と保存

独立クラス比較はcost、riding、waiting、first_wait、board、alight、legs、distanceを
全目的地・全waiting state・全alternativeで照合する。board/alightは元のOccurrence番号のまま。
さらに全OD、4種類のsample、除外なし/系統0/1/7のPlanで、State、Execution、費用・距離・乗換数を比較する。
最終構成の実マップの完全Plan比較は1,255,161,055アサーション成功。
全確定/全推定/混在の500系統合成入力、80種の小さい入力、heap・SIMD独立検査は
13,977,690アサーション成功。SIMDのscalar強制fallbackも独立に通過した。
反復駅、NoLoad/NoUnload、強制降車、途切れた区間、0 dwell、共通区間と通常Ride、途中折返しを含む。
既存の同点・分散・途中公開・到着系統除外の回帰も維持する。
予算1/4/5で独立した元クラスと比較し、それぞれ2,928,170 / 1,203,221 / 1,088,226
アサーションが成功した。通常の最終製品ビルドでは全693 CTestが成功した（88.22秒）。

| 保存形式 | 再生 |
|---|---|
| JPSD v1〜v8 | 既存のsections/estimatesフラグと旧グラフ・旧ヒープ・旧seed走査を使う |
| JPSD v9 / passenger_periodic v11 | optimized=falseとして旧操作数と公開途中状態を再生する |
| JPSD v10 / passenger_periodic v12 | 現行表と保持表それぞれにoptimizedフラグを保存する |
| JPSD v11 / passenger_periodic v13 | 現行表と保持表それぞれにintegratedフラグを追加。v10はRangeなしのグラフ・Work手順で再生する |

v4/v5のpublication換算と再生中の旧wire保持も維持する。
旧表は再生・構築を終えてから通常tickで最適化済み表への置換を始め、完成行ごとに旧行を退役する。
旧世代のフロンティアを新しいグラフやヒープに解釈し直さない。
同じ新アルゴリズムでもCPU速度によって公開を早めず、Stepの決定的な操作数だけで進める。
StepLoad、準備バリア、ネットワーク絶対参加期限は変更しない。

Rangeの基底駅と各仮想辺の緩和にそれぞれ1 Work、heap popに1、CSR末尾処理に1、
Label初期化に1/state、公開用Labelコピーに1/state、行公開に1を課金する。
除外waiting stateは元から辺が存在しないため課金しない。metadataを共用しても仮想辺の課金を省略しない。
範囲内offsetは再生によって復元され、予算1と大きな予算の完成結果・総Workは一致する。
seed索引の走査数など旧版と異なるWorkはアルゴリズムフラグで区別する。

統合版の固定グラフは58,929ノード、61,923個別辺、157,805 RangeEdge、合計219,728 CSR要素。
展開される論理辺810,897本は旧版と等しい。物理CSR要素は72.9%減少する。
メモリ入場判定は物理descriptorの構築・SoA領域と、論理辺に基づくheapの保守的上限を別々に課金する。
allocator容量は診断に限り、入場条件へ使わない。

## メモリと残る負荷

実マップの完成Label領域は旧・新とも4,543,071,984 byte。
Occurrence縮約は永続waiting Label行を縮めない。診断のarray_bytesはallocator overheadを含まない。
旧検索Label作業領域は約2.83MB、最終SoAは約3.06MB。
Radixのバケットヘッダは使用cargoだけ遅延確保し、空バケットの保持量は凍結した辺数・状態数から制限する。
空cargoの全表へバケット配列を埋め込まず、DBのstack使用量を抑える。
逆向きCSRではincoming索引約3.24MBを除去する。
最終の全配列容量は4,666,571,482から4,635,480,774 byteへ約31.1MB減った。
これは保持中の完成表を含む値で、最大一時使用量ではない。
heap容量は旧194,208、新935,752 byte。単一製品プロセスのRSSは実マップtick試行で別途記録する。

依然として全目的地で約39億回の辺緩和が必要で、次いでSectionRideの約6.91億回の検査が残る。
探索範囲を狭めたり、代替候補を削ったりしてこの数を減らしてはいない。

## 通常simulationと実際の保存・MP検証

表構築の純粋な比較には基点の独立クラスを使う。
通常tickの旧実行ファイルは既存の`bea07371bd315d58f91c52a55243195cc91e5e01`製
（SHA-256 `4925735f64f3da699a214c2e3b27489be374f7e3f748a1c1782a60cf914e4d38`）を使った。
基点との差分はnetwork参加進捗とそのテスト、設定コメントだけで、offlineの
ゲーム・旅客探索ソースは一致する。Release/assert/LTOと英語langのhashは一致していたが、
後に旧バイナリは通常版・静的CRT、新バイナリはdedicated版・DLL CRTだったことを確認した。
PEのDLL依存とVSプロジェクトのRuntimeLibraryでもこの差を確認した。
そのため、この組のtick値は構成差を調べる予備試行とし、採用の最終比較には使わない。
最終のゲーム比較は通常版・静的CRTへ揃え、実際のrelease定義と依存DLLを記録する。
通常版の新旧ReleaseのClCompile設定は、includeディレクトリを除く全項目で一致した。
旧バイナリのmanifestにある14個の製品ソースも、CRLF/LFを正規化して記録コミットと照合し、

## 目的地単位の並列化案

今回は実装しない。不変のサービス・CSRを共有し、workerごとに独立したSoA/ヒープ/非公開行を持つ。
workerの完了順を公開順にせず、従来どおり昇順の目的地と決定的な操作cursorを唯一の公開基準にする。
先行計算はderived cacheとして保存せず、保存されたcursorまでだけを公開済み状態として再生する。
必要行のworkerが遅い場合はsimulationを進めず待ち、空きCPU・壁時計による採否や行の飛ばしを禁止する。
joinの絶対期限も延長・リセットしない。

実装時には未完成workerを待ち続けるより、主スレッドが従来のStepを続けるfallbackを優先する。
先行行ごとの正確なWorkと公開コピーの境界を記録し、既存のcursorと同じprefixだけを課金・公開する。
先行行の保持数には固定の上限を置く。非公開の先行計算結果を捨てても保存再生が一致することを条件にする。

最終測定のDijkstraは準備込み時間の約81%で、この部分だけを8 workerへ移す理想上限は約3.5倍。
初期化・代替候補も移して並列部分を90%にできれば約4.7倍だが、帯域と行書込みが制限する。
2〜4倍程度は評価候補の仮説にすぎず、今回の実測改善としては報告しない。
