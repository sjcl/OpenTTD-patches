## Phase 1: 待機イベントと乗車

駅・CargoType の所有者を GoodsEntry/StationCargoList に結び付け、期限付きの
活動リストを `(期限, StationID, CargoType)` 順で処理する。通常 tick では
全駅を走査しない。列車の積載に先行して、DB の tick の直後に呼ぶ。
全国上限は 8,192 操作/tick、駅・cargo の量子は 256 Packet/tick。
量子を消費した駅は次 tick へ送る。未処理駅の古い期限を保持し、世代更新の
走査範囲と cursor を固定することで、継続流入による古い仕事の追い越しを防ぐ。
消費枠は既存の保存項目から復元し、診断値やローカルな索引の常駐状況で変えない。

実マップの初回比較で、過去の admitted search の枠待ちマーカーを引き継いだ旅客が、
表を照会しても経路を得られなかった後に翌 tick 再試行を続ける問題を発見した。
4,096 tick で61,025,723 Packetを処理し、schedulerだけで190.65秒を消費した。
この版の平均68.58ms/tickは採用結果から除外し、修正前の比較資料として残す。
`fa91456e04` は非 Memory の表照会で残っていた枠待ちマーカーを解消する。
未解決集団の登録は保持するので、行の公開・世代変更や実際の列車到着で再評価できる。
表のメモリ入場を拒否された場合の既存の admitted planner への退避は維持する。

枠待ち修正後も全国上限32,768では、平均は38.98から33.96msへ改善した一方、
p95が68.96から84.67ms、p99が87.88から99.00msへ悪化した。
通常運転の山を抑えるため、`a2915e1844` で全国枠を8,192へ変更した。
この版では世代が古い Journey も、到着時に新しい表の Intent を集団で検証し、
実際に選ばれたPacketだけを更新する。全国枠を消費済みでも部分積載でき、
読み取り専用の照会ではIntent・期限を変えない回帰を加えた。

表の行の公開時は未解決旅客を持つ駅だけを起こす。設定変更・世代失効では
所有者登録から索引も復元し、列車も新規流入もない駅を取り残さない。
積載時は既存の乗車索引が選んだ OD 集団へ表を照会する。照会結果を集団で共有し、
実際に選ばれた Packet を確定してから予約・積載する。通常の NoLoad/NoUnload、
実車、乗換時刻、強制降車、容量、部分予約と返却の検証を通す。

`passenger_journey_stats` に pending、overdue、oldest_ticks、on_time、
maximum_station_backlog、arrival_candidates、arrival_passengers、
unresolved_missed、packets、groups、scheduler_us を追加した。
到着時人数と未確定による見送りは集団代表人数による推定で、後者は表が Building
かつ乗車検証が失敗した候補の上限推定。満員や運行条件との因果分離はできない。
maximum_station_backlog はタイマー登録時と明示的診断で観測した最大値である。
pending の詳細走査は明示的な統計照会時だけに行う。
対象外cargoに残った旅客メタデータや、事前計算を無効化したリストは
pending/overdue/oldestと最大値の集計から外す。旧版の統計にはこれらが混入し、
最古期限が保存の0 tickに見える問題があった。終了セーブをsimulationを進めず
再読込し、全canonical状態を照合したうえで、正しい対象範囲の値を確認した。

## Phase 2: 初期構築と決定的な再開

サーバーは初期準備の frame を固定し、準備完了まで NetworkReceive/NetworkSend
と接続管理を続ける。既存 peer は同じ frame で準備し、全員の READY 後に解放する。
既に Map/DoneMap の peer も対象とし、先行する保存から当該 frame へ追い付くまで
待つ。準備中の新規マップ要求は MapWait に入れる。
READY は frame ACK と独立し、表の公開操作数を壁時計で決めない。
通常更新ではグラフ準備の間だけバリアに入り、旧表を保持する。
行の置換計算全体を待たず、グラフ準備後は通常運転と固定枠の行公開を再開する。

`StepLoad()` をサーバーの保存再生にも再利用する。初回の fleet 取り込みと
グラフ・共通区間の主要ループは、主 simulation thread 上の coroutine に分割した。
途中の取り込みは保存する service cursor/世代をまだ消費しない。
構築前の入力と既存の保存済み tree cursor から再現するため、保存形式を増やさない。
複数 cargo のメモリ入場判定も同じ順序・固定 byte charge を用いる。
標準ライブラリの sort、allocation、SectionGap 等には原子的な部分が残り、
8 ms は外側の目標時間であって厳密な実行時間上限ではない。

## Phase 3: 参加進捗の濫用防止

`network.max_join_time_total` を追加した。既定 900 秒、設定範囲 60–3,600 秒。
認証完了から Active まで、MapWait、ダウンロード、再生、追い付きを通じた絶対期限で、
状態遷移や進捗通知では開始時刻を更新しない。無進捗期限は別の steady_clock で管理する。
進捗は厳密増加かつサーバーが保存送信時に固定した上限以下に限る。
通知は burst 16、継続 4 件/秒の token bucket で制限する。
MapProgress は last_frame/last_frame_server/token ACK を書き換えない。
GetMap は Authorized だけ、ACK は PreActive/Active だけで受理する。

グラフ準備中も実行済み coroutine step を通知に含める。グラフ部分の通知 credit は
UINT32_MAX で打ち切り、tree 操作数の保存 cursor とは分離する。
この上限は遠隔での実 CPU 作業の証明ではなく、占有を有限にする保証は絶対期限が担う。
この部分を含め、passenger_periodic v10 と JPSD v8 の保存レイアウトは変更していない。

## 計測方法と結果

製品は MSVC x64 Release、assert ON、LTO OFF。
CPU 測定用には既存の read-only inspector と正確な StateTicks driver をコピー TU へ挿入する。
実輸送追跡は別バイナリとし、`OPENTTD_PASSENGER_TRACE=1` 時だけ有効。
Packet ID と新規生成 tick の決定的ハッシュで約1/64の Packet を選び、
その中央の1人を追う。追跡開始は最大65,536標本までとする。
分割・結合・部分配送でも標本の位置を保持し、実車の毎 tick の位置と実乗降を記録する。
ロード済み旅客は左打切り、未到着旅客は右打切りとして、完了旅行の分布と区別する。
乗車前の待機と乗換後の待機を別々に数え、実際の乗換降車も記録する。
初期の既知OD旅客は設定変更前に登録し、保存Packet IDと人数位置で両方式を照合する。
配送・未到着・途中消失を記録し、標本収支を確認する。途中消失は完了旅行に含めない。
旅行時間の分布はPacket中央の標本に対する値で、全人口を人数加重した推定ではない。
距離は実車座標の Manhattan 移動量、単位は1/16 tile。
乗車機会の見送りは、実積載の対象候補として観測され、空き容量があった実車に限った標本値。
別旅客が後から容量を消費し得るため、その値だけでは不合理な拒否を断定できない。
種別はグループ階層の最も近い名前から「特急・快速・普通/各停・準急・急行」等の
明記を拾う。全乗降人数は実車とそのグループで分類し、判別不能は
unclassified とする。標本の系統別集計では終了時のグループ名も併用するため、
共有系統の分類が食い違うものは mixed_groups とする。
利用者から、グループ名に種別があることが多いが対応表はないとの
回答を得た。これは名前による推定であり、order 数を種別へ読み替えることはしない。

入力の実マップは既存 v10 保存、SHA-256
`6783a500f47435a342a36e9a6544e33bb38f041abe91e9e2ff2c654edd16c978`。
488,096 Packet、既知 OD 806,628 人を含む。
JP+ Multiple Units に既知の容量変更警告があるため、警告件数とエラー停止解除も記録する。

製品へ復帰した最終の全 CTest は **671/671 成功**（86.82秒）。
修正後の事前計算回帰と明示的な合成ベンチマークは、合わせて
**70ケース・558,308アサーション成功**。
枠待ちマーカーを引き継ぐ追加条件は、修正前に601アサーションが失敗し、
修正後は既知の経路なし・行の構築中の両方で休眠と公開後の復帰を確認した。
追加した更新準備の回帰は2,000台の共有実車を使い、準備終了まで StateTicks、
保存 DB、旧表の行数を保持し、終了後も新表の tree 操作数が0のままであることを確認する。

進捗修正後の実 MP は参加直後と **1,037 tick** 後で全比較項目が一致した。
参加開始から667.05秒（サーバー自身の初期保存再生の待機を含む）、
クライアント再生は15,083 slices、最大 loop 43.86ms、進捗通知237件。
再生中は StateTicks `3181095005` と frame 0 が不変だった。
終了時の Packet は509,520、既知 OD は776,449人、支払い検査正常。
サーバーの company deliveries は21,553から69,443へ増えた。
この試行は通常更新のグラフ分割を追加する前の版であり、以下の最終版試行と区別する。

### MP の設定変更と予測 frame

`1dbc033a73` の実マップ MP 試行は、既定の参加期限で正常に参加し、接続したまま
事前計算設定を無効化・再有効化し、その後 **1,030 tick** の実輸送を進めた。
参加直後、設定変更の準備完了時、輸送後の全 canonical 比較項目が一致した。
再有効化では StateTicks `3181095005` を保ったまま 4,636 行を完成し、
通常運転中の frame 9365 の自動更新でもグラフ準備だけを待って旧表で再開した。
最終状態は Packet 507,753、既知 OD 776,540人、company deliveries 68,953、
支払い検査正常。参加は636.33秒、試行全体は1,151.02秒で、サーバー自身の
初期再生待ちも参加時間に含む。クライアント再生は14,439 slices、最大38.01ms。
サーバー peak working set は6,426,996,736 bytes、クライアントは5,546,217,472 bytes。

最終runtime `a2915e1844` の実マップ試行も成功した。参加639.68秒、
全体705.50秒、輸送1,074 tick、進捗通知229件。
参加直後と輸送後の全canonical項目が一致し、支払い検査も正常だった。
再生は14,529 slices、最大48.31ms、tree操作4,284,707,345。
再生中のStateTicks `3181095005` とframe 0は不変。
終了はPacket509,067、既知OD774,088人、company deliveries72,660。
サーバーpeak working set 6,423,531,520 bytes、クライアント5,541,756,928 bytes。
クライアントのprocess CPUは331.30秒、サーバー338.94秒。
通知待ち修正後のネットワークコードは、この最終runtimeまで変更していない。

クライアントは許可済み frame 範囲の中でサーバーより先に次のグラフ準備へ
到達できる。この時点で READY を送ると、サーバーがまだ開始していない
バリアへの応答となる問題を独立レビューで発見した。クライアントは先行して
準備しても、その frame のサーバー通知を受け取るまで READY を送らず停止する。
`frame_freq=20` の追加試行では実際に17回この待機を観測し、5,019 tick 後も
全項目が一致した。小さな時刻表付き fixture で大規模グラフと同じ中断を
起こすため、この通信試行だけコピー TU の初回グラフ量子を1にした
（製品は1,024）。CPU・実マップ品質測定にはこのバイナリを使用しない。

最初の MP 試行は、グラフ準備中の進捗を報告できず無進捗期限で切断された。
これは修正前の失敗として残す。修正後は実行した coroutine step を有限の
進捗 credit に含め、絶対期限は一切延長しない。進捗偽装、停止、同値、上限超過、
微小増分、過剰送信、独立した複数クライアントの期限は fake clock による
実装ヘルパーの回帰で確認した。実回線での同時攻撃クライアント群の負荷試験は未実施。
独立した読み取り専用レビューは、最終の通知待ち修正を含めて残存する
期限延長・ACK 偽装経路を指摘しなかった。

warmの平均simulationは34.5%、Journeyは56.4%、p99は41.0%減った。

process CPU・peakメモリにはロード、停止中の表構築、保存も含み、

輸送量を減らしたことだけでCPUが下がった観測ではない。
乗換降車と乗車の減少は見られるが、未完了旅客を含む総数の比を旅行当たりの
平均乗換数へ読み替えることはできない。

warmのschedulerは5,912,653 Packet・2,933,578集団、20.340秒。
updateは6,803,760 Packet・3,424,069集団、25.125秒。

updateが166,217/53/0。観測最大駅滞留は10,151/9,326。
arrival候補は6,747,902/8,019,197、未確定見送り上限観測は2,194,194/3,831,139。
これらは反復照会で同じ旅客を再計上し得るため、固有人数や実際の取り残し人数ではない。

### Phase 4: 24,576 tickの実輸送

両方式を同じ入力から24,576 tick（約332ゲーム日）進めた。
従来側は27,368標本、事前計算側は34,197標本を登録し、上限には達しなかった。
途中から登録された左打切り標本の数は異なる。新規生成から追えた標本と、
両方式で同一の初期7,349人を主な比較対象とする。
両方式とも全標本・新規標本の配送＋未到着＋消失が開始数と一致し、追跡抜けは0。
新規標本の元目的地以外への配送は両方式とも0だった。

事前計算の追跡試行では、外部の `cl:64896` が1回競合として記録された。
ゲームはexit 0、指定tick数、終了セーブ、支払い検査を満たしたが、

同試行は固定StateTicks区間の輸送品質だけに採用し、CPU・壁時計時間の比較には使わない。
CPU専用3試行はすべて競合なし。追跡バイナリ自体の時間も性能比較には使っていない。

従来側16,384 tick地点も、初期登録方式の異なる以前の完走結果と全一致した。
追跡器はゲームRNGを使わず、経路の公開・イベント処理量を壁時計で変更しない。

### 個別の品質悪化

最大の初期標本の悪化はOD3222→400（開始時の位置は3221）。従来側は
系統302（船橋連絡バス）→69の2乗車、実移動379/16 tile、1,654 tick。
事前計算側は544→376→586→245→69の5乗車、4,789/16 tile、18,560 tickだった。
OD971→916にも、385→387→385を経由して6.72倍になった標本がある。
新規OD3393→3394は両側4標本で、距離と乗車時間がほぼ同じ一方、
平均所要時間は985.75→5,360.5 tickとなり、主な差は出発前の待機だった。
これらの実移動記録と関係系統のmanifestは `transport-triage.json` に残す。

全体の配送・乗換・往復は改善したが、待機尾部と個別の大迂回が残るため、
輸送品質を全面合格とは判定しない。実際の空席・到来時刻・表の評価コストを
同時に記録していない例では、容量競合・時刻表情報・経路方針の原因分離は未完了。
追加の読み取り専用診断では、系統302の両停車のtravel/wait値は
518/74、444/74だが確定フラグはすべてfalse、公開period=0・stops=0・vehicles=0。
系統604も数値は保存されていたが確定フラグがfalseで公開period=0だった。
`PassengerPrecomputedTable::BuildGraph` はperiod<=0のサービスを除外する。
したがって、運行中の接続が表の対象外になる条件を実マップで確認できた。
これは大迂回に寄与し得る未対応条件であり、各到着での拒否理由すべてを
一意に証明するものではない。系統709はperiod33,785、実車4台のうち既知位相3台で、
位相不明を含む周期には保守的な待ちを使う条件にも該当した。

保存された未確定の数値を確定時刻表として扱うと、予測の確実性の契約が変わる。
残る対応は、未確定な所要時間の見積りと、表にない連絡を含む既存バックエンドとの
比較を設計・検証することである。今回の待機イベント・MP境界修正ではこの契約を変えていない。
診断前後のcanonical24項目は全一致、simulationは0 tick。
追加した4ODの直後照会はすべてBuildingだったため、その照会を輸送中の
個別選択の再現結果としては使わない。

## Phase 5: 保存・再現性と統合

空表構築は、通常の無効化callbackで保存済み行を破棄し、再有効化した状態で測った。
空表の0行・0操作を記録してから、simulationを進めず4,636行を完成。
グラフは686パターン、4,636駅、51,928状態、626,272辺、tree操作4,259,611,387。
構築149.977秒、プロセス全体は287.273秒・CPU444.984秒、peak working set6.405GB。
後者には入力のロード再生・保存も含む。前後の待機501,751人とStateTicks
`3181095005` は不変、支払いも正常だった。
この測定hookは既存の公開サービスsnapshotからグラフと行を完成させる。
未公開サービスの通常更新は残るので、製品の初期捕捉・通信バリア全体の時間とは異なる。

この完成セーブの再ロードは268.153秒・CPU274.156秒、peak working set6.324GB。
追加warm処理は156µsで、完成済み行の再構築を行う測定ではない。
再ロード前後のcanonical24項目は、行数・操作数を含めて全一致し、
simulationは0 tick。両試行とも他の測定・ビルドとの競合なし。

入力は既存passenger_periodic v10、JPSD v8。永続フィールドを追加していない。
Packet人数・目的地・Intent・経由、イベント期限・cursor・dirty・消費枠、
駅の待機順序、実車の予約・積載、支払い・feeder share、表世代・cursor、
配送実績をcanonical digestと個別値で比較する。
ローカル索引やキャッシュは比較対象の保存状態へ入れず、再構成後の輸送が一致する
回帰と、実MPの独立プロセス間比較で確認した。

通常tick、空表からの停止中構築、保存済み表のロード再生、保持行付き更新、
MP途中参加、接続後の再有効化、多数の待機旅客、同時刻の多数実積載APIを
それぞれ区別して検証した。計測ツールは初期設定の変更前と終了時を記録する。
CPU試行は指定tick数だけStateTicksが進んだこと、終了セーブがあること、
他の測定プロセスとの競合がないことを必須条件とした。
誤ったエラー停止・終了フックで無効になった初期試行は採用比較から除外し、
失敗記録として残した。

## 残る制約

- Phase 4には待機時間の悪化と個別の大迂回が残る。時刻表未確定の連絡が表から
  除外される実例を確認しており、輸送品質の全面合格は保留。
- 8msのロード準備目標は厳密な実行時間上限ではない。sort、allocation、SectionGap、
  一部のロード・索引構築は原子的で、最終実MPの観測最大sliceも48.31msだった。
- メモリ上限で事前計算を入場拒否した場合は既存のadmitted plannerを使う。
  その状況まで全国探索が常に0であるという保証はしない。
- 不正な進捗と複数参加者の期限はfake clockで検証したが、実回線上で多数の
  攻撃クライアントを同時接続する負荷試験は実施していない。
- Windows/MSVCで検証した。Linuxなど別toolchainのビルドは未実施。
- 入力NewGRFには既知の容量変更警告がある。計測専用TUでエラー停止を解除し、
  警告と解除件数を記録した。製品のエラー停止方針は変更していない。
- 種別はグループ名による推定で、区間運転は保存された名目停車パターンの
  保守的な部分集合判定である。迂回・往復の合理性や見送りの原因を、これらの
  件数だけですべて自動判定するものではない。

コンパクトな生データ、失敗試行、SHA-256、再現手順は
[measurement evidence](measurements/passenger-routing-integration-2026-10-15/README.md) に残す。
大きな入力セーブ、資産、実行ファイルはignoredな `build-integration` に保持する。
